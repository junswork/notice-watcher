# 개발기록 — 공지사항 알림이

2026-09-05 ~ 09-07. 웹사이트를 감시해서 카카오워크로 알리는 프로그램을 만들며
알아낸 것들. **다음에 비슷한 걸 만들 때 처음부터 다시 알아내지 않으려고** 남긴다.

---

## 1. 이런 걸 또 만들 때 순서

1. **대상 페이지를 먼저 받아 본다.** 코드를 쓰기 전에 `curl` 로 받아서 목록이
   HTML 안에 있는지 확인한다. 있으면 브라우저가 필요 없다 — 이 한 가지로
   프로그램의 무게가 완전히 달라진다.
2. **고유 번호를 찾는다.** 링크에 `bidx=`, `seq=` 같은 게 있으면 그게 열쇠다.
3. **'수정' 을 어떻게 알아낼지 정한다.** 목록에 수정일이 있으면 거기서 끝나고,
   없으면 본문까지 받아 해시를 떠야 한다. 이게 접속 횟수를 20배 가른다.
4. **바뀌면 안 되는 것과 바뀌어도 되는 것을 가른다.** 조회수·신청인원처럼
   저절로 변하는 값을 지문에 넣으면 매 실행이 '수정됨' 이 된다.
5. **첫 실행은 조용하게.** 안 그러면 첫날 알림 수십 건이 온다.
6. **깃허브 액션에 올린다.** 컴퓨터를 켜 둘 필요가 없어진다.

---

## 2. 브라우저가 필요한가 — 이 판단이 전부다

앞서 만든 예매 프로그램(`../ticketing`)은 Playwright 로 크롬을 띄운다. 좌석을
실제로 클릭해야 했기 때문이다. 그래서 **PC를 켜 둬야만** 했다.

이 프로그램은 "페이지 받아서 지난번과 비교" 가 전부다. `requests` 만으로 되고,
그러면 깃허브 서버에서 공짜로 돌릴 수 있다.

| | 예매 프로그램 | 이 프로그램 |
|---|---|---|
| 하는 일 | 클릭·입력 | 읽기·비교 |
| 필요한 것 | 크롬 + Playwright | `requests` |
| 어디서 도나 | 내 PC (켜 둬야 함) | 깃허브 서버 |
| 실행당 시간 | 수 분 | 10초 |

**로그인이 필요해도 브라우저가 꼭 필요한 건 아니다.** 아래 5번 참고.

## 3. 과기대 게시판 (로그인 없는 곳)

### 세 곳이 같은 게시판 프로그램을 쓴다

대학공지·학사공지·생활관공지 모두 링크가 `?do=commonview...&bidx=숫자` 꼴이고,
상세 페이지는 `table.tbl_view` 안에 제목·작성자·조회수·날짜·첨부파일·본문이
들어 있다. 화면 모양(표 / 카드)만 다르고 속은 같다. **파서 하나로 셋을 처리한다.**

새 게시판을 붙일 때 이 패턴인지부터 확인하면 작업이 5분에 끝난다.

### 함정 1 — '수정일' 항목이 없다

본문만 고치면 목록의 제목·날짜가 그대로다. **목록만 봐서는 수정을 알 방법이
전혀 없다.** 그래서 상세 페이지 본문까지 받아 해시를 뜬다.

### 함정 2 — 조회수를 지문에 넣으면 안 된다

조회수는 누가 열어볼 때마다 오른다. 넣으면 **매 실행이 '수정됨'** 이 된다.
같은 글을 반복 조회해 조회수가 595 → 599 로 오르는 동안 해시가 그대로인지
확인해 두었다 (`test_hash_ignores_views`).

이런 값은 어느 사이트에나 있다: 조회수, 신청인원, 남은 좌석, 광고 배너, 시각
표시. **지문에 넣을 것을 고를 때는 "사람이 안 건드려도 변하나" 를 묻는다.**

### 함정 3 — 목록 맨 위는 고정공지다

날짜순이 아니다. 대학공지는 위 6건, 학사공지는 8건이 고정공지라 자리를 먹는다.
15건만 보면 실제 신규는 7~9건만 덮인다. **1페이지 전체(25건)를 보게 했다.**

### 함정 4 — 제목을 목록에서 읽지 않는다

맨 위 배너형 게시물은 링크 글자가 '자세히 +' 라서 제목이 아니다. 목록에서는
번호만 뽑고 **제목은 상세 페이지에서 읽는다.** 어느 화면 모양이든 똑같이 동작한다.

### 인코딩은 문제가 아니었다

콘솔에 한글이 깨져 보여서 EUC-KR 인 줄 알았는데, 실제로는 UTF-8 이 맞고
윈도우 콘솔 출력 문제였다. **바이트를 직접 디코딩해 확인하고 나서 판단한다.**

## 4. 접속 횟수를 줄인 방법 (성능)

처음에는 매 실행마다 목록에 걸린 글의 상세를 전부 열었다. 그 상태로 주기를
5분으로 줄이면 학교 서버를 종일 두드리는 꼴이 된다.

**새 글은 목록만 봐도 안다.** 처음 보는 번호가 있을 때만 그 글의 상세를 연다.
새 글은 하루 몇 건뿐이라 평소에는 열 페이지가 없다.

실측 (게시판 3곳, 새 글이 없는 평상시):

| | 접속 | 긁는 시간 | 깃허브 실행 | 주기 |
|---|---|---|---|---|
| 새 글 확인 | **3번** | **0.6초** | 10초 | 5분~1시간 |
| 수정 확인 | 54번 | 18.4초 | 52초 | 하루 2번 |

**접속이 18배 줄었다.** 이 분리 덕분에 공지가 몰리는 평일 오전에 5분마다 돌 수
있다. 깃허브 실행 시간에는 체크아웃·파이썬 설치가 8초쯤 포함돼 있다.

54번은 1페이지에 실제로 걸린 글 수(21 + 20 + 10)에 목록 3번을 더한 것이다.
`DETAIL_LIMIT` 은 25지만 게시판이 그만큼 안 채우면 그만큼만 연다.

어느 일정이 깨웠는지는 워크플로에서 `github.event.schedule` 로 알 수 있다.
크론마다 다른 모드를 주면 **워크플로 파일 하나로** 두 가지를 돌린다.

```yaml
WATCH_MODE: ${{ github.event.inputs.mode || (github.event.schedule == '7 4,13 * * *' && 'full' || 'new') }}
```

## 5. 로그인이 필요한 사이트 (에픽폴리오)

**브라우저 없이 통과했다.** 다음에 학교 계열 사이트를 뚫을 때 그대로 쓴다.

### 로그인 절차를 읽는 법

로그인 버튼에 걸린 자바스크립트를 읽으면 절차가 그대로 나온다. 여기서는:

1. 로그인 페이지에 RSA 공개키(`#RSAModulus`, `#RSAExponent`)가 박혀 있다.
2. 아이디·비밀번호를 각각 RSA 로 암호화해 `/common/user/encSo.do` 에 보낸다.
3. 서버가 돌려준 값을 포털 로그인 API 로 POST 한다.
4. **포털이 '자동 제출 폼' 을 돌려준다. 그걸 다시 보내야 끝난다.**

### 4번이 핵심이다 — 여기서 막혔다

3번까지 다 되는데 세션이 안 붙었다. 포털 응답은 숨은 폼 + `document.forms[0].submit()`
이 담긴 페이지였고, 브라우저는 그걸 자바스크립트로 곧바로 다시 보낸다.
**우리는 자바스크립트를 안 돌리니 거기서 멈춘 것이다.** SSO 에서 아주 흔하다.

폼을 찾아 대신 보내 주면 통과한다 (`epic.follow_auto_submit`).

> **진단의 결정적 단서:** 사람이 브라우저로 하면 15초 걸리는데 내 코드는
> 0.7초에 실패했다. **같은 일을 하고 있지 않다는 뜻**이다. 시간 차이가 크면
> 단계를 빠뜨린 것이다.

### RSA 는 라이브러리 없이 된다

브라우저가 쓰는 jsbn 의 `RSAKey.encrypt` 는 PKCS#1 v1.5 라 스무 줄이면 된다.
`pow(m, e, n)` 이 파이썬 기본 기능이다. 의존성을 늘리지 않았다.

주의할 점 하나 — **jsbn 은 결과 hex 를 키 길이에 맞춰 0 으로 채우지 않는다.**
자릿수가 홀수일 때만 앞에 0 을 하나 붙인다. 이걸 맞춰야 서버가 받아준다.

### 검증은 가짜 계정으로 했다

암호화가 맞는지 확인하려고 `test0000` 으로 암호화해 서버에 보냈더니
`dGVzdDAwMDA=`(base64 "test0000") 로 정확히 복호화해서 돌려줬다.
**진짜 계정을 쓰기 전에 암호화 구현부터 검증할 수 있다.**

### 로그인 사이트에서 지킨 것

- **최소 확인 간격**(3시간). 일정이 5분마다 깨워도 건너뛴다.
- **실패해도 재시도하지 않는다.** 연속 실패는 계정 잠금이다. 다음 실행에서
  한 번 더 해보는 것으로 충분하다.
- **사람이 채우는 로그인 창은 절대 재전송하지 않는다.** 자동 제출 폼만
  따라간다. 안 그러면 빈 아이디로 로그인을 다시 시도하게 된다.
- **불필요한 접속을 지운다.** 처음엔 로그인 뒤 홈 화면을 3번 불렀다. 자동 제출
  표시(`.submit()` / `onload=`)가 있는 페이지만 따라가도록 고쳤다.

### 암호화된 ID 를 열쇠로 쓰지 마라

에픽 목록의 프로그램 ID 는 `encSddpbSeq` 라는 암호화된 값이다. **세션마다
달라질 수 있다.** 그걸 열쇠로 삼았다면 매 실행이 '전부 새 프로그램' 이 되어
알림이 쏟아졌을 것이다. 제목으로 구분하게 했다.

이름에 `enc`, `token`, 세션과 함께 나오는 긴 16진수는 의심한다.

## 6. 놓치지 않기 위한 규칙

이 프로그램의 목적은 "중요한 기회를 놓치지 않는 것" 이다. 그래서 애매하면
**중복 알림이 오는 쪽으로** 틀리게 했다. 조용히 놓치는 것보다 낫다.

- **알림을 먼저 보내고, 성공한 것만 기록한다.** 순서를 뒤집으면 전송이 실패한
  공지는 영영 다시 안 온다.
- **게시판 한 곳이 실패해도 그 게시판 기록은 건드리지 않는다.** 다음 실행에서
  다시 본다. 다른 게시판은 정상 진행한다.
- **상세 하나를 못 받으면 그 글만 건너뛴다.** 기록하지 않으니 다음에 다시 본다.
- **목록이 비면 예외를 던진다.** 화면 구조가 바뀐 것을 '새 글 없음' 으로
  삼키면 조용히 죽는다. 빨간불로 남긴다.
- **1페이지 전체를 본다.** 감시가 반나절 멈췄다 재개돼도 그 사이 글이 밀려나
  안 잡히는 일이 없도록.

### 죽은 감시기가 제일 나쁘다

알림이 안 오는 것은 두 가지다 — **공지가 없어서** 조용한 것과 **감시가 멈춰서**
조용한 것. 겉보기가 똑같다. 사람은 잘 돌고 있다고 믿는데 실은 아무것도 안 보고
있는 상태가 만들어진다. 감시 프로그램을 만들 때는 이 구분을 반드시 넣는다.

- **연속 실패하면 알린다.** 한 번 실패로는 안 알린다 — 서버가 잠깐 느린 일은
  흔하다. 세 번 연속이면 사람에게 말한다. 같은 대상으로는 하루 한 번까지만.
- **살아 있다는 신호를 따로 보낸다.** 프로그램이 통째로 안 돌면 실패 알림조차
  못 보낸다. 그 경우는 **아무 일도 안 일어나는 것**으로만 드러나므로, 주기적인
  생존 신호가 유일한 통로다. 평일 아침 한 번이면 충분하다.
- 실패 알림도 **채널이 살아 있어야** 간다. 알림 채널 자체가 죽은 경우는 생존
  신호가 안 오는 것으로 알아챈다.

## 7. 깃허브 액션에서 알게 된 것

### 상태를 저장소에 되커밋한다

"어디까지 알렸는지" 를 `state.json` 에 담아 워크플로가 직접 커밋한다.
DB 가 필요 없고, 커밋이 남아서 **60일 무활동 자동 중지**도 저절로 피한다.

### 반드시 해야 하는 설정

새 저장소는 워크플로가 **읽기 전용**이다. 이걸 안 바꾸면 state 커밋이 실패하고
**같은 알림이 계속 온다.** 겉보기엔 잘 도는 것 같아서 놓치기 쉽다.

```bash
gh api -X PUT repos/<계정>/<저장소>/actions/permissions/workflow \
  -F default_workflow_permissions=write
```

### 무료 사용량

| 저장소 | 무료 시간 | 15분 주기(월 2900분) |
|---|---|---|
| 공개 | 무제한 | 가능 |
| 비공개 | 2000분 | **한도 초과** |

비밀은 전부 Secrets 에 있으니 **공개 저장소로 두는 게 낫다.**

### 크론은 UTC 다

한국 시간에서 9를 뺀다. 요일 지정도 UTC 기준이라 새벽 시간대는 요일이 밀린다.
짜고 나서 24시간이 빈 곳 없이 덮이는지 계산해 봤다.

최소 주기는 5분이고, 깃허브가 바쁘면 몇 분 늦는다. **적은 주기는 최소 간격이지
보장 시각이 아니다.**

### Secrets

- **`gh secret set` 으로 넣는 게 빠르다.** 웹 UI 를 열 필요가 없다.
- **한 번 저장하면 값을 다시 볼 수 없다.** 화면에 값 칸이 비어 보이는 게 정상.
- 들어갔는지는 실행 로그로 확인한다. 설정된 것은 `***`, 안 넣은 것은 빈칸.
- **워크플로 `env:` 에 이름을 나열해야 넘어간다.** 빠뜨리면 조용히 빈 값이 된다.

### `.gitattributes` 를 넣는다

`state.json` 을 윈도우(로컬)와 리눅스(깃허브)가 번갈아 커밋한다. 줄바꿈을
고정하지 않으면 내용이 같은데도 파일 전체가 바뀐 것으로 보인다.

```
* text=auto eol=lf
```

## 8. 카카오워크 봇

`../ticketing/notifier.py` 에서 발송 부분만 가져왔다. 경고음·반복 발송은 뺐다 —
깃허브 서버에는 스피커가 없고, 공지사항은 결제창처럼 5분 안에 끝나는 일이 아니다.

- **봇 만들 때 Callback URL 은 비워 둔다.** 그건 사용자가 버튼을 눌렀을 때
  이벤트를 받기 위한 것이다(`submit_action`, `call_modal`). 보내기만 하는 봇은
  필요 없다. 버튼을 달려면 **항상 켜져 있는 서버**가 필요해지고, 그러면 깃허브
  액션으로는 못 한다.
- **대화방 id 는 한 번만 조회해 캐시한다.** 매번 열면 알림 한 건이 요청 세 건이 된다.
- **받는 사람을 이메일로 지정한다.** 안 하면 워크스페이스 첫 번째 멤버에게 간다.
- **게시판마다 다른 봇을 쓸 수 있다.** 앱키를 인자로 받게 하고, `boards.json`
  에는 **앱키가 아니라 앱키가 든 환경변수 이름**을 적는다. 앱키를 파일에 적으면
  저장소에 그대로 올라간다.

---

## 9. 도구를 쓰다 배운 것

- **`.env` 는 파일에서 파일로 복사한다.** 값을 화면에 찍지 않으면 안전하다.
- **`gh` 가 있으면 저장소 생성·push·Secrets·권한 설정까지 다 된다.** 사람이
  꼭 해야 하는 건 `gh auth login` **한 번뿐**이다. 이걸 늦게 깨달아서 Secrets 를
  손으로 등록하게 했다. 도구가 생기면 앞서 한 안내를 다시 판단해야 한다.
- **셸 heredoc 안에서 파이썬 정규식을 쓰지 마라.** 따옴표와 `\n` 이 뭉개진다.
  파일 편집 도구를 쓰거나, 정규식은 문자열로 조립한다.

## 11. 알림이 너무 많아지면 — LLM 분류와 관심도 점수

**만들지 않았다.** 지금은 필요 없어서다. 다만 다음에 이런 걸 또 만들 때 바로
꺼내 쓸 수 있게 방법과 근거를 적어 둔다.

### 언제 필요해지나

실측한 발생량 (2026-09 개강 주간, 게시판 4곳 합계):

```
09-01: 6건    09-02: 6건    09-03: 11건    09-04: 6건
-> 하루 평균 6건, 최대 11건, 월 180건쯤
```

지금은 이 알림이 **전부 똑같이 생겼다.** "장학금 마감" 과 "매점 아르바이트
모집" 이 같은 무게로 온다. 이 상태로 양이 늘면 눈이 미끄러지기 시작하고,
그러면 **알림은 오는데 놓치는** 상태가 된다. 원래 막으려던 것과 같은 결과다.
그 조짐이 보이면 이 절을 편다.

### 분류는 LLM 호출 한 번이면 된다

새 글은 어차피 상세를 열어 본문을 갖고 있다. 그걸 그대로 넘겨 구조화된 값을
받는다 — 분야, 성격(기회/정보/변경), 대상, 마감일, 행동필요 여부, 관심도 점수.
한국어 행정문서는 학습 데이터 없이 첫날부터 읽힌다.

Anthropic 파이썬 SDK(`anthropic`)를 쓰고, 구조화 출력은
`client.messages.parse()` 또는 `output_config={"format": ...}` 로 받는다.

**비용 (2026-06 기준 단가, 월 180건 · 건당 입력 1000 / 출력 200 토큰 가정):**

| 모델 | 입력/출력 $/1M | 월 비용 |
|---|---|---|
| `claude-opus-5` | $5 / $25 | 약 $1.8 |
| `claude-sonnet-5` | $2 / $10 | 약 $0.7 |
| `claude-haiku-4-5` | $1 / $5 | 약 $0.36 |

**월 2천원이면 아껴서 얻을 게 없다.** 판단이 틀려 기회를 놓치는 값이 훨씬 크다.
프롬프트 캐싱은 이 빈도(하루 몇 건)에서는 캐시가 살아 있지 않아 도움이 안 된다.

### 학습 모델을 만들지 마라 — 프로필을 써라

이게 이 절에서 제일 중요한 대목이다.

하루 6건이면 라벨이 월 180개다. 분류기를 학습시키려면 수백~수천 개가 필요하니
**반년은 모아야** 쓸만해진다. 그동안 아무 도움이 안 된다.

대신 관심사를 **글로 쓰면** 오늘 당장 동작한다.

```
기계공학과 3학년. 하반기 공채 준비 중.
관심: 취업(대기업 제조), 자격증, 장학금, 교환학생, 어학시험
관심 없음: 봉사활동, 문화행사, 대학원, 생활관 시설 공지
```

학습된 가중치보다 이쪽이 낫다. **왜 그렇게 판단했는지 읽을 수 있고, 상황이
바뀌면 한 줄 고치면 된다.** 공채가 끝나면 그 줄을 지우면 그만이다. 학습 모델은
둘 다 못 한다.

정말 학습 효과가 필요하면, 사람이 남긴 판단을 **프롬프트에 사례로 넣는다.**

```
[과거 판단]
"[채용설명회] 현대건설 (9월 10일)" -> 유용했음
"[인권센터] 평등한 캠퍼스 캠페인" -> 불필요했음
```

사례가 쌓일수록 정확해진다. 훈련 인프라가 필요 없고 20~30개만 모여도 달라진다.
다만 이 피드백을 자동으로 모으려면 버튼이 필요하고, 버튼은 콜백 서버를 부른다
(아래 참고). 사람이 가끔 적어 주는 것으로 충분하다.

### 점수가 생기면 알림을 3단계로 나눈다

| 점수 | 처리 |
|---|---|
| 높음 | 즉시 알림 |
| 중간 | 하루 한 번 요약으로 묶기 |
| 낮음 | 조용히 기록만 |

**낮은 것도 버리지 않는 것이 핵심이다.** 요약에는 전부 들어간다. 판단이
틀려도 하루 한 번 훑을 때 걸린다. 이 안전망이 없으면 필터가 곧 기회를 삼키는
장치가 된다. 자동 판단을 넣을 때는 **틀렸을 때 사람이 알아챌 통로**를 같이
만든다.

### 콜백 서버 — 깃허브로는 안 된다

카카오워크 메시지에 버튼을 달려면 콜백 URL 이 필요하다. 깃허브 액션은 정해진
시각에 깨어나 일하고 죽는 실행기라 **요청을 기다릴 수 없다.** Pages 도 정적
파일뿐이다.

`POST /repos/{owner}/{repo}/dispatches` 가 외부에서 워크플로를 깨우는 주소이긴
하지만, 깃허브 토큰을 헤더에 넣어야 하고(카카오워크는 자기 형식으로 쏘므로
불가) 즉시 응답도 못 준다.

**대안:** Cloudflare Workers / Deno Deploy / Vercel 같은 곳에 함수 하나를 올리면
된다. 컴퓨터를 켤 필요는 여전히 없고 이 정도 양은 무료 한도 안이다. 다만
배포할 것과 토큰과 고장 날 곳이 하나씩 는다. **버튼이 정말 필요해지기 전에는
파일 하나를 고치는 편이 낫다.**
