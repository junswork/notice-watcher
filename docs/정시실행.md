# 정시에 돌게 하기 — 밖에서 깨우기

깃허브의 예약 실행(`schedule`)은 **몇 시간씩 늦는다.** 무료 공개 저장소에서는
깃허브가 한가할 때만 처리하기 때문이다. 실측(2026-09-07, 예약 실행 9회):

| 크론에 적은 주기 | 실제 간격 평균 | 최악 |
|---|---|---|
| 5분 (평일 오전) | **87분** | 87분 |
| 15분 | **119분** | **260분** |
| 1시간 | 133분 | 142분 |

**설정이 무엇이든 실제로는 두 시간쯤마다 돈다.** 생존 신호가 09:02 예약인데
12:41 에 온 것도 이 때문이다.

반면 **API 로 깨우면 곧바로 돈다.** 그래서 밖에 있는 무료 cron 서비스가
정시에 두드리게 한다.

```
cron-job.org  --(POST + 토큰)-->  깃허브 API  -->  워크플로 즉시 실행
```

기존 `schedule` 크론은 **지우지 않는다.** 외부 호출이 끊겨도 느리게나마 계속
돌아야 한다. 둘 다 있으면 지금보다 나빠질 경우가 없다.

---

## 1. 토큰 만들기 — 권한을 좁히는 것이 핵심

https://github.com/settings/personal-access-tokens/new

| 항목 | 값 |
|---|---|
| Token name | `notice-watcher-cron` |
| Expiration | 1년 (만료되면 알림이 끊기니 달력에 적어 둔다) |
| Repository access | **Only select repositories** → `notice-watcher` 하나만 |
| Permissions → Repository permissions → **Actions** | **Read and write** |

**다른 권한은 전부 No access 로 둔다.** 특히 `Contents` 에 write 를 주면 안 된다.

이유가 중요하다. 이 토큰은 남의 서버(cron-job.org)에 저장된다. 새어 나갔을 때
무슨 일이 벌어지는지가 권한으로 결정된다.

| 권한 | 할 수 있는 일 | 유출되면 |
|---|---|---|
| **Actions: write** | 이미 있는 워크플로를 실행 | 감시가 몇 번 더 돌 뿐. 무해 |
| Contents: write | 저장소에 코드를 push | **Secrets 를 찍는 워크플로를 심을 수 있다** |

Secrets 에는 카카오워크 앱키와 **학교 통합 계정**이 들어 있다. `Contents` 는
절대 주지 않는다.

> 같은 이유로 `repository_dispatch`(`POST /repos/{owner}/{repo}/dispatches`)를
> 쓰지 않는다. 그 엔드포인트는 `Contents: write` 를 요구한다. 우리가 쓰는
> `workflow_dispatch` 는 `Actions: write` 면 된다.

토큰 값은 만들 때 한 번만 보인다. 바로 복사한다.

## 2. cron-job.org 에 등록하기

https://cron-job.org 가입 후 **Create cronjob**. 아래 세 개를 만든다.

모든 작업에 공통으로 넣을 것:

| 항목 | 값 |
|---|---|
| URL | `https://api.github.com/repos/junswork/notice-watcher/actions/workflows/watch.yml/dispatches` |
| Request method | **POST** |
| Timezone | **Asia/Seoul** (UTC 로 환산할 필요가 없어진다) |
| Headers | `Authorization: Bearer <토큰>` <br> `Accept: application/vnd.github+json` <br> `Content-Type: application/json` |

성공 응답은 **204 No Content** 다. 본문이 비어 있는 것이 정상이다.

### 작업 1 — 새 글 확인 (제일 중요)

- 일정: **매일 08:00~21:00, 5분마다**
- 본문:
  ```json
  {"ref": "master", "inputs": {"mode": "new"}}
  ```

게시판당 접속이 한 번뿐이라 5분마다 돌려도 학교 서버에 부담이 없다.

### 작업 2 — 수정까지 확인

- 일정: **매일 13:07, 22:07**
- 본문:
  ```json
  {"ref": "master", "inputs": {"mode": "full"}}
  ```

게시물 상세를 전부 다시 읽어 접속이 쉰 번쯤 된다. 하루 두 번이면 충분하다.

### 작업 3 — 생존 신호

- 일정: **평일(월~금) 09:02**
- 본문:
  ```json
  {"ref": "master", "inputs": {"mode": "new", "heartbeat": "true"}}
  ```

공휴일은 코드에서 거르므로 cron-job.org 쪽은 요일만 맞추면 된다.

> 밤 시간대(21시~08시)는 등록하지 않았다. 그 시간에는 공지가 거의 안 올라오고,
> 깃허브의 예약 실행이 느리게나마 받쳐 준다.

## 3. 확인하기

작업을 만든 뒤 **Run now** 를 눌러 본다. cron-job.org 실행 기록에 **204** 가
찍히고, 깃허브 Actions 탭에 `workflow_dispatch` 로 실행이 뜨면 성공이다.

동작은 미리 확인해 두었다 — 같은 요청을 손으로 보내 세 경우 모두 맞게 돌았다.

| 보낸 것 | 로그 |
|---|---|
| `{"mode":"new","heartbeat":"true"}` | `WATCH_MODE: new` / `HEARTBEAT: 1` / 생존 신호 발송 |
| `{"mode":"new","heartbeat":"false"}` | `HEARTBEAT:` (빈 값) — 생존 신호 없음 |
| `{"mode":"full"}` (heartbeat 생략) | `WATCH_MODE: full` / `HEARTBEAT:` (빈 값) |

`heartbeat` 를 문자열 `"false"` 로 보내도 꺼진다. 깃허브가 boolean 으로 바꿔
준다. 생략해도 마찬가지다.

## 4. 잘 되는지 나중에 보는 법

며칠 뒤 실제 간격을 다시 재 본다.

```bash
gh run list --repo junswork/notice-watcher --limit 60 \
  --json createdAt,event --jq '.[] | [.createdAt, .event] | @tsv'
```

`workflow_dispatch` 가 5분 간격으로 촘촘히 찍혀 있으면 성공이다.

## 이게 고장 나면

**cron-job.org 가 죽어도 감시가 멈추지는 않는다.** 깃허브 예약 실행이 남아
있어 느리게 계속 돈다. 다만 다시 두 시간 주기로 돌아가므로, 아래 신호로
알아챈다.

- **아침 생존 신호가 안 온다** — 작업 3이 멈췄다는 뜻이다. 토큰 만료가 가장
  흔한 원인이다.
- **cron-job.org 실행 기록에 401 이 찍힌다** — 토큰이 만료됐거나 지워졌다.
- **403 이 찍힌다** — 권한이 모자란다. `Actions: Read and write` 인지 본다.

토큰을 새로 만들면 cron-job.org 의 세 작업 헤더를 모두 고쳐야 한다.
